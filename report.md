# Vibe coding a personal finance app: a first-hand case study

## Introduction

I report my first experience with vibe coding: building a personal finance application through natural-language interaction with an AI coding tool, without manually writing code. The application was developed using Flask, SQLite, Bootstrap, and Jinja templates.

My goal is to reflect on what it means to develop a non-trivial software system when the AI writes all the code. I am particularly interested in the implications of this workflow for software engineering expertise, requirements formulation, maintainability, testing, documentation, and technical debt.

At this stage, this text is primarily a working report for myself. However, I also intend it to be readable by graduate students and colleagues who may be interested in AI-assisted software development. The orientation is therefore closer to a case study than to a purely personal narrative.

The main questions guiding this reflection are:

* How far can an application be developed through vibe coding?
* What role does the human play when the AI writes all the code?
* What kinds of software engineering expertise remain useful?
* How does this workflow affect code quality, maintainability, testing, and documentation?
* What risks emerge when software is developed incrementally through AI-generated patches?
* What evidence should be collected to support a more systematic analysis later?

## Background and motivation

I was a senior developer until around 2011 and continued to follow software development practices and large-scale software leadership until around 2020. Since then, I have had almost no time to devote to programming. This project was partly a way to reconnect with programming practice and partly a way to understand vibe coding through direct experience.

The technology stack combined familiar and unfamiliar elements. I had experience with older versions of Bootstrap, especially Bootstrap 3, and substantial experience with SQLite, although I am more proficient with MySQL. I had no prior experience with Flask. My last major programming project had been in PHP using CodeIgniter 3.

Before starting, I did not expect the AI coding tool to be as capable as it turned out to be. I was surprised by its ability to generate consistent, running code from scratch. One of my motivations was to examine whether a software engineering background is necessary for this kind of workflow, and what level of programming and software analysis proficiency is required to obtain production-grade software generated by AI.

I am not ready to answer that question definitively. My current view is that someone with a basic understanding of programming could probably build a working application through vibe coding. However, the resulting code might become difficult to understand, evaluate, and maintain without stronger software engineering knowledge.

## Project context

The application is a personal finance app. The original motivation was to use large language models to automatically categorize transactions from bank statements. This motivation came from my own experience: I used to categorize transactions manually in the 2000s, but eventually stopped because the process was too time-consuming.

The initial goal was relatively focused: upload a CSV file of transactions, categorize them, maintain a live dashboard, and track personal finances. The project began on April 28, 2026. It was developed through Codex using GPT-5.5 in Medium intelligence and Fast mode. After approximately six days of work, I had spent around USD 100 beyond the free daily limit. I expect that the final cost may reach two or three times that amount.

I briefly tried a smaller GPT-5.3-mini model with standard time after adding credits, but each prompt took close to ten minutes. I used it for only a small number of prompts before switching back.

I have retained the full chat history and maintain an SVN commit history, with at least one commit per day. These artifacts may support a later analysis of the project by allowing reconstruction of the prompt history, implementation sequence, daily evolution, errors, corrections, and scope expansion.

## The human role: from coding to software analysis

I did not write a single line of code myself. My contributions consisted of specifying what I wanted, testing the application, evaluating behavior and appearance, adjusting GUI and UX aspects, providing feedback when something failed, and occasionally inspecting generated code.

In that sense, the AI clearly built the application: it wrote the code. However, I played several roles during the process, including developer, architect, tester, product owner, and UX designer. The best description of my role is probably **software analyst**.

I knew what the user wanted, but I also had enough technical knowledge to guide the implementation, identify risks, and decide when the generated system required review or cleanup. This is an important interpretation of the experience: vibe coding did not remove the need for technical judgment. It changed where that judgment was applied.

I felt in control throughout the project. This may be related to my background in model-driven engineering. In that context, it is normal to design thoroughly and then generate code automatically. The difference is that model-driven engineering usually relies on deterministic templates and explicit models, whereas vibe coding allows requirements written in natural language to be translated directly into code.

I was not controlling the code line by line. I was controlling the project by steering the AI, defining requirements, testing results, and deciding what to accept.

I therefore do not feel that I built the app in the sense of writing it. The AI built it. The analogy is a software company: the product owner may have the idea and the rights, but the developers wrote the product. In this case, I acted more like the product owner, analyst, tester, and reviewer, while the AI acted as the developer.

## Prompting as lightweight requirements engineering

Most prompts were short, usually one or two sentences. Sometimes I used meta-prompting with ChatGPT to generate more thorough instructions before sending them to Codex.

I began to think of a prompt as similar to the first instruction one gives to a developer when asking for a feature to be implemented. In this sense, prompting felt like a form of lightweight requirements engineering. The quality of the generated implementation depended partly on how clearly the desired behavior was expressed.

Some prompts were small and exploratory. For example:

> Have another deeper look at `default_category_rules.json`. Do I really need all of them?

In that case, the AI suggested changes, and I decided which ones to apply.

Other prompts were more concrete and operational. For example:

> In the categories, remove:
>
> Cafe/Snacks should be in Restaurant
> Pharmacy/Health should be renamed to Health
> Transfer should be Uncategorized
> Fees/Interest should be renamed to Fees
> Credit/Refund should not exist, use the category based on the description.
>
> Add a category Shopping which includes WALMART, DOLLARAMA.
>
> Add a category Home which includes HOME DEPOT, DECATHLON.
>
> In the rules, AGENCE DE MOBILITE DURABL should be Transport.
>
> ALIMENTAIRE should be in Restaurant.

The most complex prompt concerned a conservative transaction categorization pipeline. It specified merchant normalization, user-defined rules, built-in rules, LLM classification for unknown transactions, batching, deduplication, confidence thresholds, strict JSON output, and preservation of existing app behavior. For more complex functionality, natural-language instructions became closer to structured requirements documents.

The AI was particularly effective at renaming concepts and updating dependencies across the application. For instance, I could ask it to rename “import format” to “statement type,” predefine statement types such as checking account and credit card, and consider whether other account types were relevant. The AI handled this kind of conceptual refactoring well, consistently updating both back-end and front-end elements from natural-language instructions.

When the AI misunderstood my intent, I generally took responsibility for it. I assumed that I may not have put enough thought or detail into the prompt. However, I would have appreciated more clarification questions from the AI. Such questions would likely have helped in cases where my prompt was underspecified.

This suggests that one important aspect of a future workflow is deciding how precise, formal, and detailed prompts should be, and when the AI should be expected to ask questions before implementing.

## How the application evolved

The project began with a focused objective: upload bank statement transactions, categorize them, and maintain a live dashboard for personal finance tracking. The central idea was to use LLMs to help categorize transactions automatically.

The scope expanded as the app began to work and as I saw what was possible. Additional features emerged, including:

* a rule-based categorization pipeline;
* default categorization rules;
* saved user rules;
* LLM-based categorization when no rule matched;
* user verification of LLM decisions;
* a more evolved dashboard;
* year-over-year comparisons;
* asynchronous jobs;
* a settings page;
* more user control over import and categorization.

I did not expect the project to go this far at the beginning. The application idea evolved as the application itself evolved.

The rule categorization pipeline was the most complex and risky part of the app. It involved default rules, saved user rules, LLM calls when the category was unknown, and user verification of LLM decisions. It also required attention to cost, because unnecessary LLM calls could become expensive.

The asynchronous jobs feature was also notable. I expected it to require more than a single short prompt, but it was implemented quickly. That surprised me.

## Speed, productivity, and cost

The AI wrote code very quickly, usually within about a minute. This was one of the most striking aspects of the experience. I was skeptical because no human developer would implement comparable changes that quickly.

The speed was impressive, but it also raised concerns. Fast implementation does not automatically imply that the code is optimized, maintainable, or free of hidden complexity.

After about a week, the application felt stable and more than an MVP. From a user perspective, it was close to production grade. The ability to add or modify functionality through natural language was highly productive. Back-end and front-end changes were usually updated consistently.

Compared with paying professional developers, even a final cost two or three times higher than the initial USD 100 would still be small. As a professor, I often have graduate students implement software for research. Compared with that mode of development, AI implementation required only a fraction of the time. The quality is probably not far off either, considering recent graduate student profiles.

I was nevertheless surprised by how quickly I exhausted the USD 100 budget. The cost did not discourage me from asking for quality-improving work, such as refactoring, testing, documentation, or architectural review. However, model choice mattered. The smaller model I tried was too slow for this workflow, so I switched back. I also wanted to use Sonnet, but it was very expensive. This experience suggests that future projects should consider the trade-off between model cost, model quality, and interaction speed.

## Testing, verification, and trust

After each modification, I manually tested the application. Testing usually meant running the app, exercising the changed feature, checking whether the behavior matched expectations, and evaluating the appearance.

At the beginning, I inspected the generated code more often to make sure I was steering the project in the right direction. Later, I mostly judged changes by running the app and checking behavior and appearance, while still performing occasional code spot checks.

When something failed, I reported it to Codex using error messages, screenshots, or descriptions in my own words. Crashes happened rarely. Poor UI choices were more common than functional failures. At some point, I became dissatisfied with the generic GUI and spent time improving the UX and GUI.

I began to trust the application because it worked and continued to work as the feature set grew. I currently trust the app’s behavior and the generated codebase to a similar degree. However, the discovery of legacy elements created the need for a code review.

The app works well from a user perspective, but I still need to assess whether the internal code quality is sufficient for long-term maintenance.

## Legacy code, technical debt, and maintainability

In this project, “legacy code” means earlier AI-generated code. Everything in the app is AI-generated, but some code was generated for earlier versions of the app and may no longer fit the current design.

One example involved a setting field stored in JSON format to define the type of statements. I asked the AI to move it to a text field with just the type name, because that was more user-friendly, and to update the database. It did so, but kept the JSON format in the database. I had to explicitly ask it to correct this.

Another example concerned functions or variables with names containing the word “Legacy.” These names appeared because the AI wanted to preserve backward compatibility with earlier versions. I had to explicitly ask it to analyze their use and dependencies and remove them.

I have not observed major uncontrolled technical debt so far. The AI has managed growing complexity surprisingly well. However, the app was implemented through patches, so the possibility of old, dead, redundant, or suboptimal code remains. This is one of the main reasons I want to run a thorough code review.

The code seems good, but I am not sure it is optimized. For example, I had to explicitly ask the AI to optimize the database with indexes. As a human developer, I would likely have implemented indexes earlier because I could foresee uses such as search and filtering.

This suggests that the AI can implement requested functionality well, but may not proactively anticipate architectural or performance concerns unless asked.

## Planned code review, refactoring, tests, and documentation

The next step is to ask the AI to perform a thorough code review. The review should focus on architecture, coding style, redundant code, dead or legacy code, uniformity, modularity, and maintainability. I particularly want the code to be maintainable by a human, even though it was entirely vibe coded.

The planned code review prompt is:

```markdown
You are a senior software developer. You care about software architecture, coding style, and overall high-quality code. With a fresh pair of eyes, perform a thorough code review of the entire project. Consider state-of-the-art code quality.

I already know the project is missing comments, a README file, documentation, and unit tests. These will be handled later. In your code review, pay special attention to redundant code and dead or legacy code. Ensure there is a uniform coding style. You particularly value modular code with at least three tiers: presentation, logic, and data.

Although this app has been entirely vibe coded, a human must be able to maintain it. For now, give me a comprehensive list of all the points your review has revealed. Classify them into three categories: CRITICAL, IMPORTANT, and NICE TO HAVE.
```

I expect that a series of refactorings will be necessary after this review.

The AI did not create tests, a full README, documentation, or code comments unless explicitly asked. I think this is reasonable: some users may only need a prototype. The app did at least generate an empty README and a minimal `requirements.txt`. Still, this shows that quality practices need to be introduced intentionally into the workflow.

Once the codebase is more stable, I plan to ask the AI to create:

* comments for non-obvious code sections;
* a consistent file-level preamble style;
* comments for all public routes;
* unit tests for all core functionalities;
* a README file for developers;
* documentation or a tutorial for end users.

Based on my experience with AI as a judge in other tasks, such as academic writing and paper reviewing, I expect the AI code review to be critical but partly generic. Some feedback may be applicable to many projects. I still expect the review to be valuable and to improve quality, maintainability, and optimization.

However, I also plan to manually review the full codebase afterward. Some issues are project-specific. For example, because the app makes LLM calls, I asked the AI to analyze where those calls happen and ensure that they are minimal and controlled. This kind of cost-related concern is not something I would fully delegate to an AI review.

## Relation to model-driven engineering

My background in model-driven engineering shaped how I interpreted the experience.

There is a broad similarity between model-driven engineering and vibe coding: in both cases, the human works at a higher level of abstraction and code is generated automatically. However, they are not the same.

Model-driven engineering is about designing using domain-specific languages and then generating code or performing analysis. It often requires formal models, deterministic transformations, and explicit design artifacts.

Vibe coding is different. Requirements written in natural language are translated directly into code. There is no need to go through a design pipeline such as UML.

An open question is whether including a design phase would result in more efficient and effective code. I am not ready to answer this yet.

## Emerging interpretations

Several interpretations are beginning to emerge from this experience.

First, vibe coding does not eliminate software engineering expertise. It changes where that expertise is applied. The human contribution shifts from writing code to specifying functionality, steering implementation, testing behavior, reviewing results, and managing quality.

Second, working software can emerge quickly from short natural-language prompts. This creates major productivity gains, but it also creates skepticism because complex implementation happens much faster than expected from human developers.

Third, AI-generated code can become legacy code quickly. Even in a one-week-old project, earlier AI-generated code may no longer fit the current design. Patch-based development can leave outdated data formats, backward compatibility layers, old names, or unused code paths.

Fourth, quality practices are not automatic. Tests, documentation, comments, indexing, architectural review, and maintainability improvements do not necessarily happen unless explicitly requested. A proper vibe-coding workflow will likely need explicit checkpoints for these activities.

Finally, the boundary between prototype and production is blurred. The app quickly became more than an MVP and feels close to production grade from a user perspective. However, production-grade behavior from the user’s point of view is not the same as production-grade internal quality. Code review, refactoring, tests, documentation, and optimization are still needed.

## Open questions for continued reflection

I am not ready to define a complete workflow for future vibe-coding projects until this project is finished. However, several issues should be considered:

* What should the initial prompt contain?
* How detailed should prompts be?
* When should refactoring happen?
* When should code review happen?
* When should tests and documentation start?
* How should functionalities and changes be formulated?
* When and how should generated changes be verified?
* Should a design phase be included?
* Would UML, architecture diagrams, schemas, or structured requirements improve the result?
* What level of software engineering background is necessary?
* Can someone without strong programming experience produce a reliable app?
* Can they produce a maintainable app?
* How effective will AI-generated code review and tests be?
* How much manual review remains necessary?
* What is the real cost of producing production-grade software through vibe coding?

## Current conclusion

This experience suggests that vibe coding can produce substantial, working software very quickly.

The application is already more than an MVP and feels close to production grade from a user perspective. The AI has been effective at implementing functionality, managing growing complexity, and propagating changes across the stack.

At the same time, the experience highlights the need for explicit software engineering discipline. Code review, refactoring, testing, documentation, optimization, and maintainability work do not happen automatically. They must be intentionally introduced into the workflow.

The main preliminary conclusion is that vibe coding does not remove the need for software engineering expertise. It changes the human role from manual coding to analysis, specification, verification, and quality control.
